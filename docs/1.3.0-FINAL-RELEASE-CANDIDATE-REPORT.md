## Download-speed diagnosis

The discrepancy was reproduced with the retained real yt-dlp executable, version `2026.10.26`, SHA-256 `f5389d3698ecde4ef06f4e6b1ce0294fe9ac1396228c8990b8d3416d6d177a7d`. An owned loopback HTTP server supplied generated transfer bytes using the production progress arguments. No private source, authenticated account or user installation was used. The payload is a transfer fixture, not playable-media qualification.

The old UI read `progress.speed` directly. In the observed HTTP downloader, that value is the average payload rate since the current download/resume started, rather than the recent interval rate shown by a network monitor. A second issue sampled only the latest per-job snapshot each dashboard tick, which could miss transfers that started and finished between ticks. A finished record retained its whole-transfer average into finalization. Finally, binary rates were labelled `MB/s`, making comparison with decimal bit-rate displays ambiguous.

| Probe | Configured transfer | Recorded result |
|---|---|---|
| Constant rate | 24 MiB at 2 MiB/s | Exact 25,165,824 output bytes, yt-dlp exit 0; approximately 2,097,065 B/s after warm-up; 17 progress records on stdout and none on stderr |
| Rate change | First 8 MiB at 2 MiB/s, remaining 16 MiB at 12 MiB/s | Exact output bytes and exit 0; adjacent counters show 11.94–12.16 MiB/s in the fast interval while yt-dlp's cumulative average rises only from 3.11 to 4.50 MiB/s |
| Specific fast interval | Counter at elapsed 5,694.44 ms = 18,838,455 bytes | Recent interval **12.00 MiB/s** versus the old UI input **3.72 MiB/s** |

These measurements reject the initial hypothesis that normal progress was lost on stderr in this tool/fixture. The first probe's server callback marked a closed response as aborted after all bytes had been written; output length, raw progress and tool exit establish successful transfer. It is not presented as an independent failed download.

The implemented correction:

- Derives recent per-invocation speed from adjacent byte counters and monotonic time. A resume counter, rollback or new stream establishes a baseline instead of inventing transferred bytes.
- Clears current speed/ETA on finished progress while retaining any final observed byte increment for the graph.
- Accumulates observed payload bytes under the existing canonical queue lock. The existing dashboard timer divides its byte delta by actual elapsed time; statistics and graph use that same sample, including jobs completed and removed between ticks.
- Uses explicit `KiB/s`, `MiB/s` and `GiB/s` labels in Classic/Modern rows, graph and progress notifications; ordinary file-size formatting is unchanged.
- Rejects nonfinite/negative values that could poison the graph or fail ETA conversion. Localized help in all 16 languages explains that 1 MiB/s is approximately 8.39 Mbps.

Evidence and detailed implementation boundaries: [speed investigation](../artifacts/speed-organizer-20261117/SPEED-INVESTIGATION.md), [constant probe](../artifacts/speed-organizer-20261117/speed-local-probe/result.json), [variable probe](../artifacts/speed-organizer-20261117/speed-local-variable-probe/result.json), [interval comparison](../artifacts/speed-organizer-20261117/speed-local-variable-probe/rate-comparison.json). The 14 deterministic-clock telemetry cases are included in the 103-case targeted lane.

This is **observed media payload throughput**, not an OS per-process network counter. Protocol overhead, unrelated process traffic, metadata requests, FFmpeg disk I/O and bytes before the first observed counter are excluded. Progress-report granularity affects timing. A single finished-only report does not invent traffic from an existing file. A just-finished transfer can appear in its final graph interval and reaches zero in the next idle interval. A queue row can retain its last reported interval rate until another progress/terminal event; it is not independently sampled NIC traffic. No claim is made that every Task Manager display must equal the application number.

## Organizer diagnosis and correction

The owner's list contained **122 records and 118 distinct source identities**. The inspected folder contained **59 adjacent JSON + MP4 pairs**. All 59 JSON files were readable. **Only one pair's exact source identity appeared on the list; 58 had identities absent from it.** Ignoring identifier case did not increase the overlap. The list hash was unchanged after the read-only comparison.

Therefore, the observed `1 / 122` match count was not a reproduced JSON-reading defect in this dataset. Matching a title, filename fragment or merely any adjacent JSON would authorize unrelated recordings and is intentionally not added. Source identity, variant, active-job, collision, canonical-reference and sidecar checks remain required.

There were real presentation defects that obscured the result:

- Each row began with the same long exported list name, causing its distinguishing URL to disappear behind ellipsis.
- Planning deliberately selected the first successful match in the inspector even when that match was on another page. A page of missing URLs could therefore be accompanied by an unrelated successful file's details.
- The operation-finalization localization call reset the inspector heading to generic “Details”, hiding its status. Long details could retain their previous scroll position.

The correction adds counts of scanned media, media with an indexed source identity, identified media outside all imported lists, and unidentified media. Counts represent distinct files rather than duplicate list entries or multiple canonical references. **Indexed identity does not mean the file is authorized to move.** Existing whole-file/sidecar validation still makes that decision.

Rows now begin with their URL or media filename. Full list provenance remains in accessibility text and the inspector. Details begin with status/reason, URL and source identity; the long list name follows. The inspector follows the current visible page/filter and retains the explicitly inspected row while it remains visible. Empty filters clear stale details/candidates. The new compact diagnostic increases card height by its own measured text height, preserving the previous row viewport and the 40-row materialization cap. All three diagnostic strings are translated in 16 locales.

Synthetic regression coverage includes:

1. A 122-row list / 59 sidecar-pair reproduction with exactly one shared identity, 117 missing records and four duplicate records. Unrelated files remain non-candidates; attempting to move the entire mixed result is refused. Moving and undoing the single verified pair preserve hashes and do not create History or queue entries.
2. Distinct-file counts across duplicate lists and redundant History/queue/JSON references, plus an unidentified file and corrupt JSON. Duplicate destinations remain conflicts.
3. A long list name, 40 visible missing rows and an off-page successful match. The inspector stays on a visible row, preserves a visible inspected row during refresh, follows page/filter changes and clears on an empty filter. No move is performed by viewing or filtering.
4. The existing 10,000-entry/40-row presentation cases and bounded actions at TextScale 100/150/200 in the targeted lane.

JSON parsing and placeholder validation also passed for all four newly translated keys in all 16 language files. This is structural localization validation, not native-speaker editorial approval.
